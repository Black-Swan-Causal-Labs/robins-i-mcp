## Built

**`server.py`** — 8 tools. **`scaffold.py`** — per-domain question/cue scaffolds,
split out so the scaffold logic is testable without the MCP layer, mirroring how
target-mcp separates `assess.py` from `server.py`. **`retrieve.py`** — a genuine
straight lift from target-mcp; its only dependencies are `SectionMap`,
`build_bundle`, `extract_file` and `parse_text`, all of which have compatible
signatures here. **`pyproject.toml`** and a real `.venv`, since the project had
been running on target-mcp's interpreter and a server needs its own entry point.
**`tests/test_server.py`** — 44 tests, hermetic, synthetic paper, no PDF on disk.

Three design points that were decisions rather than transcription, all recorded
in `DECISIONS.md`:

- **`submit_answers(domain=0)` finalizes.** The settled surface had no separate
  finalize tool, and overall-level acts (escalation, override, direction of bias)
  have to happen after all six domains land. Overloading domain 0 keeps the
  surface at the agreed size and makes "no new answers, just close it out" an
  explicit call rather than an implicit side effect of the sixth domain.
- **Absence searches run at submission, not at finalization.** The 2026-08-01
  decision said absence is generated by the server; `submit_answers` is where
  that becomes enforcement. Quotes resolve there too rather than at
  `bind_evidence`, so a bad quote is rejected while the caller still has the
  domain in hand and can fix it.
- **Ratification is never self-served.** `ratified_by` is documented as
  human-only and the server never populates it.

## Deliberately not built

Both were on the settled surface and both were dropped after looking at the
source they were supposed to be ported from. Neither is a straight lift, and
pretending otherwise would have produced something shaped like TARGET's data
model rather than ROBINS-I's:

- **`render_report_docx`** — target-mcp's docx renderer is built around a
  checklist table. ROBINS-I's deliverable is a domain/judgement/support document.
  Needs its own renderer.
- **Corpus tools** (`aggregate_corpus`, `build_coding_sheet`,
  `validate_against_gold`) — written against leaves and verdicts, not domains and
  judgements. Rewrites, not ports. Needed before any gold-standard validation.

Also: `mcp` 2.0 turned out to have replaced `FastMCP` with `MCPServer` at a new
import path. Pinned `<2` to match target-mcp in production rather than migrate an
untested new server onto a new SDK in the same sitting.

## Test run — Jabagi et al., Lancet Reg Health Eur 2026

Maternal RSVpreF vs infant RSV hospitalisation, French SNDS, weighted HR 0.50.
Chosen over a PMCID fetch because it exercises the .docx supplement path and is a
genuinely different shape from Dickerman: vaccine-vs-nothing rather than
head-to-head, with durability strata.

Came out **serious**. All 26 quotes bound on the exact pass; 13 of 35 questions
never reached. The substantive findings are in `STATUS.md`; the one worth
repeating here is that domain 1 fails at **1.3, not 1.1**. Confounder *coverage*
is good — exact matching on date of birth removes the calendar-time confounding
that has troubled every other RSVpreF effectiveness study. What sinks it is that
gestational age at birth and birth weight are matched and weighted on despite
being realised after maternal vaccination, and whether RSVpreF affects
gestational duration is exactly the open safety question that confined the
French campaign to 32-36 weeks. That is a finding the algorithm produced from
the answers; it is not one the assessor set out to make, and it is flagged in the
domain support as the override point.

**The run found a real bug.** The ratification queue came back with two items and
should have had three: an agent-proposed P1 was not being queued, because the
library only checked whether the list was *empty*. So a list the model invented
read as settled the moment it was supplied — precisely the substitution the P1
gate exists to prevent. Fixed in `report.py` with a new
`prespecified_confounders_ratified` field, plus a test.

## Then: is ROBINS-I V2 only for cohort studies?

Asked at the end of the session. Answered from the source rather than memory,
which was the right call, because checking riskofbias.info turned up something
the repo had never recorded: **the 20 November 2025 release is a draft, subject
to change**, with a November 2024 release archived beside it.

That matters more than it first appears. The `algorithm_fingerprint` had been
carrying an implicit promise it cannot keep — it hashes our edge tables, so it
detects a correction *we* make, and is completely blind to a revision *they*
make. Two different failure modes; only one was covered. `SOURCE_STATUS` now
stamps the draft status onto every report's provenance line, and
`source_status` reaches clients through `get_spec`.

`spec_version` was deliberately not bumped: nothing encoded changed, so reports
carrying `robins-i-v2-cohort-0.1.0` stay comparable. Bump it when the content
moves.

On the original question I got it wrong first time and was corrected. I answered
"cohort only", following the source's parenthetical gloss "follow-up (cohort)
studies". The operative term is **follow-up**; "(cohort)" appears once, and the
phrase "cohort study" appears exactly once in 49 pages, in a time-varying
confounding example. The document never enumerates eligible designs.

The narrow reading is not a terminological quibble — it would exclude target
trial emulations, which are the central use case and which is what *both* worked
examples in this repo are. Neither Dickerman nor Jabagi is a textbook cohort
study. The criterion is structural: observed forward from a defined time zero
under the contrasted strategies. Nested case-control and case-cohort sit in a
genuinely unresolved middle that the source does not address.

I had also asserted that no other design variant exists, on one page fetch
summarised by a small model. Too strong for a negative claim; the supportable
version is that none is *published*, with separate tools reported to be in
development.

Two method lessons, both cheap: the primary source settled this and the secondary
summary did not — grepping the PDF for design vocabulary was worth more than any
description of the tool. And a single fetch is not evidence for a negative.
